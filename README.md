# Autoverify Kit

Autoverify is a minimal methodology kit for adding a verifiable autonomous experiment loop to another git repository.

The loop is:

```text
agent edits bounded scope -> verifier runs -> result is scored -> commit is kept or reverted
```

## How It Works

The kit is shipped as a `.autoverify/` directory of **reference material**. Once copied into a target repo, `.autoverify/` is read-only — no agent ever edits it. An adoption agent reads `.autoverify/` and creates a separate **harness directory** at the target repo's root (default name: `autoresearch/`). The harness directory is self-contained: it holds the operating directive, the result schema, the project-specific adapter, the verifier wrapper, and the runtime artifacts. The loop agent operates only on the harness directory and the target repo's mutable scope.

```text
.autoverify/                  <- reference material (read-only after copy)
  agent-instructions.md       orientation; adoption + loop protocol
  program.md                  operating directive (template, copied verbatim)
  result.schema.json          result contract (copied verbatim)
  adapter.md                  template with TODOs (copied, then filled in)
  run_candidate.py            stub (copied, then implemented)
  program.karpathy.md         reference example only (Karpathy's original)

<target-repo>/
  autoresearch/               <- harness directory created by adoption agent
    program.md                copied verbatim from .autoverify/
    result.schema.json        copied verbatim from .autoverify/
    adapter.md                filled in by adoption agent
    run_candidate.py          implemented by adoption agent
    runs/                     per-candidate logs (gitignored)
    results.jsonl             append-only result log (gitignored)
```

## Core Contract

The harness must provide one command (declared in `<harness>/adapter.md`):

```bash
python3 <harness>/run_candidate.py
```

That command evaluates the current working tree and emits normalized JSON:

```json
{
  "valid": true,
  "score": 0.0,
  "metric_name": "example_metric",
  "objective": "minimize",
  "status": "valid",
  "metrics": {},
  "artifacts": {}
}
```

If the verifier is weak, the methodology is weak. Keep tests, fixtures, datasets, benchmark harnesses, and scoring code outside the agent's mutable scope.

Every candidate runs under a fixed compute budget (wall clock, steps, tokens, episodes — pick what fits the domain). The budget is the comparator that makes architecturally different candidates fairly comparable on the primary metric, not just a safety timeout. Define it in `<harness>/adapter.md` and enforce it in `<harness>/run_candidate.py`.

## Adoption Protocol

The kit has two layers: **immutable methodology** in `.autoverify/` (copied verbatim, never edited), and a **project-specific harness** at the target repo root (generated by an adoption agent). The agent's job is to bootstrap the harness — not to redesign the loop.

### File roles

| Location | File | Layer | Who fills it in | Purpose |
|---|---|---|---|---|
| `.autoverify/` | `agent-instructions.md` | reference | copied verbatim | Orientation. Identifies adoption vs loop phase and defines the protocol. |
| `.autoverify/` | `program.md` | reference | copied verbatim | Template operating directive. Source for `<harness>/program.md`. |
| `.autoverify/` | `result.schema.json` | reference | copied verbatim | Result contract. Source for `<harness>/result.schema.json`. |
| `.autoverify/` | `adapter.md` | reference | template | Template with `TODO`s. Source for `<harness>/adapter.md`. |
| `.autoverify/` | `run_candidate.py` | reference | stub | Stub. Source for `<harness>/run_candidate.py`. |
| `.autoverify/` | `program.karpathy.md` | reference | example | Reference example only — Karpathy's original `program.md`. Not part of the methodology. |
| `<harness>/` | `program.md` | harness | copied verbatim from kit | Operating directive followed by the loop agent. |
| `<harness>/` | `result.schema.json` | harness | copied verbatim from kit | Result contract. |
| `<harness>/` | `adapter.md` | harness | generated by adoption agent | Project objective, scopes, budget, runner command, acceptance rule. |
| `<harness>/` | `run_candidate.py` | harness | implemented by adoption agent | Verifier wrapper. |
| `<harness>/` | `runs/` | runtime | created by runner | Per-candidate logs. Gitignored. |
| `<harness>/` | `results.jsonl` | runtime | appended by loop agent | Append-only result log. Gitignored. |

### Step 1 — Copy the kit

From this repo, copy the `.autoverify/` directory into the root of the target repository:

```bash
cp -R .autoverify /path/to/target-repo/
cd /path/to/target-repo
```

Append to the target repo's `.gitignore`:

```text
.autoverify/
```

(Harness-specific gitignore entries are added by the adoption agent in Step 2.)

### Step 2 — Run the adoption agent

Open the target repository in an agent harness (Claude Code, Codex, Cursor, Aider, etc.) and give it the prompt below. The agent reads `.autoverify/` and the target repo, then bootstraps the harness directory at the project root. It must NOT modify anything inside `.autoverify/`.

> **Adoption prompt (paste verbatim into the harness):**
>
> You are adopting the Autoverify Kit into this repository. Read `.autoverify/agent-instructions.md` first, then follow its **Adoption Phase** section exactly.
>
> Treat `.autoverify/` as read-only reference material. Do not edit any file inside it.
>
> Your output is a new harness directory at the target repo root (default name: `autoresearch/`, confirm with me if you want a different name). Inside that directory, you will:
>
> 1. Copy `.autoverify/program.md` and `.autoverify/result.schema.json` verbatim.
> 2. Copy `.autoverify/adapter.md` and fill in every `TODO` based on the target repo (objective, primary metric and direction, compute budget, hard timeout, mutable scope, immutable scope, candidate runner command, acceptance rule, anti-cheating rules).
> 3. Copy `.autoverify/run_candidate.py` and implement it: enforce the budget and timeout, persist logs under `<harness>/runs/`, print JSON matching `result.schema.json`, exit nonzero for invalid candidates.
> 4. Append `<harness>/runs/` and `<harness>/results.jsonl` to the target repo's `.gitignore`.
> 5. Run the verifier once on the unmodified working tree to establish the baseline. Append the result to `<harness>/results.jsonl` with `kept: true` and `description: "baseline"`. Report the baseline back to me.
>
> If anything in `.autoverify/` looks wrong for this project, surface the disagreement — do not silently rewrite it.

### Step 3 — Hand off to the loop agent

Start a fresh agent session (or the same harness) with `<harness>/program.md` as its operating directive. The harness must follow `program.md` literally and without deviation: it is the contract that defines the loop, the autonomy directive, the rollback discipline, and the boundaries. Anything project-specific the agent needs is in `<harness>/adapter.md`; anything about *how* to run the loop is in `<harness>/program.md` and is not negotiable.

A typical kickoff prompt:

> Read `<harness>/program.md` and follow it exactly. The project-specific configuration is in `<harness>/adapter.md`. Begin with setup, then enter the loop and do not stop until I interrupt you. Do not edit anything inside `.autoverify/` — it is read-only reference.
