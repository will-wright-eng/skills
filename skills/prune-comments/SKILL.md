<what-to-do>

Strip redundant comments from code files. Default scope is the diff against `main`, or against the base branch I name (stacked PRs); I can instead point you at a file, directory, or the whole repo. The default action is delete: a comment survives only when you can name the specific fact it carries that a competent reader could not get from the code, the names, or the types. Doubt resolves toward deletion — not toward keeping, and not toward condensing. Never touch semantic comments that tooling reads (see DIRECTIVES.md) or genuine why-comments. Modify comments only — never code, never markdown. Measure the comment ratio before and after; when I give a maximum (e.g. `15%`), keep going until every candidate file is under it or only directives and why-comments remain. Finish with a concise summary of what was removed, condensed, kept, and observed.

</what-to-do>

<supporting-info>

## Scope

Two modes, chosen by how I invoke you:

- **Diff mode (default)** — candidates are comments on lines added or modified in `git diff <base>...HEAD`, where `<base>` is `main` unless I name another branch. Pre-existing comments elsewhere in touched files are left alone.
- **Sweep mode** — I name a path (file, directory, or repo root); every comment under it is a candidate. The taxonomy and the doubt rule are the same as in diff mode. Sweep mode reaches comments humans wrote deliberately, so stale flags and code observations in the summary matter more — nobody is about to review this as a PR diff.

File scope is code and functional files with in-file comment syntax: source files, scripts, config (YAML/TOML/INI), SQL, Dockerfiles, CI definitions. Explicitly out of scope, never modified:

- Markdown and documentation files (`.md`, `.rst`, `.txt`, anything under `docs/`)
- Generated files (a "do not edit" / "generated by" header, lockfiles, build output) and vendored directories — skip them entirely

## The failure mode is under-pruning

Every comment can be rationalized into a why-comment: it mentions a reason, it might help a newcomer, it's harmless. None of those is a fact the code lacks. This skill fails when it leaves a file reading as a tutorial of itself, not when it deletes a comment a reader could have reconstructed from the code in five seconds. When you notice yourself writing "kept because it adds context", stop: name the fact or delete.

## The taxonomy

Classify every candidate comment into exactly one bucket. Remove is the default; the other three have entry conditions a comment must meet.

### Never touch — semantic comments

Comments that tooling reads; deleting or rewording them changes behavior. Read DIRECTIVES.md for per-language patterns: shebangs, encoding declarations and magic comments, linter and type-checker suppressions, coverage and security-scanner pragmas, formatter toggles, build and codegen directives, IDE structure markers, license and copyright headers, doctest examples inside docstrings. The patterns are representative, not exhaustive — a comment shaped like a machine directive (`tool:action`, short and rigidly formatted) that you don't recognize belongs here too. This is the one place doubt resolves toward keeping: an unrecognized directive-shaped comment stays.

### Keep — why-comments

A comment earns its place by carrying a fact that a competent engineer, reading the code fresh, would otherwise get wrong or be surprised by. Name the fact before you keep it; if you can't, it isn't one. Facts that qualify:

- workaround rationale, with the bug or issue it works around
- invariants and preconditions no compiler checks
- ordering, locking, and concurrency constraints
- performance rationale ("O(n²) but n ≤ 8")
- security consequences of changing the code
- references to specs, RFCs, papers, named algorithms
- non-obvious domain or business-logic reasons
- warnings to future editors ("must stay in sync with X")
- TODO/FIXME items with actionable content

The test is the fact, not the word "because". A comment that gives a reason the code already shows is a pseudo-why comment — see Remove.

### Condense — verbose why-comments and doc comments

Condense is for comments that definitely carry a fact but bury it in prose. It is not the hedge for comments you're unsure about — if you can't name the fact you're preserving, there is no fact, and the comment goes in Remove.

- a verbose why-comment → one terse line preserving the constraint
- doc comments on public API that a lint rule or docs build consumes (`help()`, Sphinx, JSDoc, godoc, rustdoc, a docstring lint rule — check the repo's lint and docs config) → keep the contract (params, returns, raises, where the ecosystem expects them), delete the restated narration; condense, never delete
- a docstring that restates the signature plus one real fact → the one real fact
- a TODO/FIXME with a paragraph of context → one line keeping the action and any ticket reference

**The doubt rule:** doubt resolves toward deletion. Not sure the comment carries a fact the code lacks → delete. Sure it carries one, but not sure the condensed version keeps it → keep the original and say so in the summary. Never condense as a compromise between keep and delete.

### Remove — redundant narration

The default bucket: everything that isn't semantic and doesn't carry a nameable fact.

- restates the adjacent code ("increment the counter", "loop over users")
- restates a name, signature, or type the declaration already shows
- docstrings and doc comments that only restate the signature, on anything no lint rule or docs build consumes — a public function without an enforced doc convention is not exempt
- **pseudo-why comments** — a reason the code already shows: "check for null because the API can return null" above a null check, "retry because the request may fail" above a retry loop, "lowercase for case-insensitive comparison" above `.lower()`
- **step headings** — a label over the next block: "validate input", "handle the error case", "build the response", "early return if empty". The block is its own heading.
- explanations of language semantics, standard-library behavior, idioms, or well-known library calls
- restated log messages, error strings, or assertion messages
- change narration addressed to a reviewer ("added this to fix the bug", "NEW:", "updated to handle nulls", "this ensures the fix works")
- decorative section banners that restate structure (but IDE-functional markers like `// MARK:` and `#region` are never-touch)
- commented-out code — git history is where dead code lives
- placeholder scaffolding above finished code ("TODO: implement")
- stale comments the code contradicts — remove, but flag in the summary: the contradiction may mean the code is wrong

Match the surrounding codebase only where a convention is enforced: a lint rule or docs build that requires doc comments (godoc on exported symbols, a docstring rule) wins even where it feels redundant. An unenforced house style — "the other files have docstrings" — does not; note it in the summary instead of obeying it.

## Comment ratio

Comment ratio is comment lines ÷ non-blank lines over the candidate lines — added lines in diff mode, the whole file in sweep mode. A line counts as a comment when it is entirely comment or docstring: line comments, block-comment bodies, docstring bodies. Trailing comments on code lines don't count.

Measure before touching anything and again after — per file for small scopes, aggregate for large ones. `cloc --git --diff $(git merge-base <base> HEAD) HEAD --by-file` reports added comment and code lines per file for diff mode; `cloc`, `scc`, or `tokei` report comment and code lines per file for sweeps. When none is installed, count with `grep -c` against the language's comment syntax on the diff's added lines.

When I pass a maximum (`15%`), any file still over it after the taxonomy pass gets a second pass over its condensed comments: delete each one whose preserved fact is recoverable from a name, a type, a test, or a doc file. Measure again. If the file is still over, stop — the remainder is directives and why-comments, and deleting those to hit a number is the wrong trade. Report the file, its ratio, and its largest remaining comment blocks so I can decide.

The ratio checks the taxonomy; it doesn't replace it. Never delete a semantic or why-comment to reach the target, and never leave redundant narration in a file because it's already under the target.

## Comments only

Never modify code — not even a rename that would make a comment unnecessary. When a comment exists because the code is unclear (a bad name, a convoluted expression), apply the doubt rule to the comment and record the observation for the summary. The code fix belongs to a later turn if I want it.

## Summary

Close with a concise report:

- **Ratio** — before and after, per candidate file; against the maximum when I gave one, naming any file still over it and what's left in it
- **Counts** — removed / condensed / kept, per file for small scopes, aggregate with notable files for large ones
- **Notable keeps** — comments that looked deletable but survived, each with the specific fact that saved it
- **Stale flags** — removed comments that contradicted the code, as possible bugs
- **Code observations** — places where the real fix is the code, not the comment; informational only, nothing changed
