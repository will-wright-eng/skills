<what-to-do>

Strip redundant comments from code files — the narration that restates what the code already says. Default scope is the diff against `main`, or against the base branch I name (stacked PRs); I can instead point you at a file, directory, or the whole repo. Delete a comment only when the code alone clearly says everything it says; when a comment is questionably load-bearing, rewrite it to minimal technical language instead of deleting. Never touch semantic comments that tooling reads (see DIRECTIVES.md) or genuine why-comments. Modify comments only — never code, never markdown. Finish with a concise summary of what was removed, condensed, kept, and observed.

## Scope

Two modes, chosen by how I invoke you:

- **Diff mode (default)** — candidates are comments on lines added or modified in `git diff <base>...HEAD`, where `<base>` is `main` unless I name another branch. Pre-existing comments elsewhere in touched files are left alone.
- **Sweep mode** — I name a path (file, directory, or repo root); every comment under it is a candidate. Sweep mode reaches comments humans wrote deliberately, so shift the doubt rule one notch conservative: where diff mode would delete, condense; where it would condense, keep.

File scope is code and functional files with in-file comment syntax: source files, scripts, config (YAML/TOML/INI), SQL, Dockerfiles, CI definitions. Explicitly out of scope, never modified:

- Markdown and documentation files (`.md`, `.rst`, `.txt`, anything under `docs/`)
- Generated files (a "do not edit" / "generated by" header, lockfiles, build output) and vendored directories — skip them entirely

## The taxonomy

Classify every candidate comment into exactly one bucket.

### Never touch — semantic comments

Comments that tooling reads; deleting or rewording them changes behavior. Read DIRECTIVES.md for per-language patterns: shebangs, encoding declarations and magic comments, linter and type-checker suppressions, coverage and security-scanner pragmas, formatter toggles, build and codegen directives, IDE structure markers, license and copyright headers, doctest examples inside docstrings. The patterns are representative, not exhaustive — a comment shaped like a machine directive (`tool:action`, short and rigidly formatted) that you don't recognize belongs here too.

### Keep — why-comments

Information the code cannot express:

- workaround rationale, with the bug or issue it works around
- invariants and preconditions no compiler checks
- ordering, locking, and concurrency constraints
- performance rationale ("O(n²) but n ≤ 8")
- security consequences of changing the code
- references to specs, RFCs, papers, named algorithms
- non-obvious domain or business-logic reasons
- warnings to future editors ("must stay in sync with X")
- TODO/FIXME items with actionable content

### Condense — questionably load-bearing or verbose

A comment that carries real information buried in narration gets rewritten to the minimal technical statement:

- a verbose why-comment → one terse line preserving the constraint
- public API doc comments → keep the contract (params, returns, raises, where the ecosystem expects them), delete the restated narration. Never delete public-API doc comments outright — `help()`, Sphinx, JSDoc, godoc, and rustdoc consume them, and some lint configs require them; check the repo's lint config before touching doc-comment structure.
- an internal docstring that restates the signature plus one real fact → the one real fact
- a TODO/FIXME with a paragraph of context → one line keeping the action and any ticket reference

**The doubt rule:** deletion requires certainty that the code alone says everything the comment says. Not certain → condense. Not certain the condensed version preserves the constraint → keep the original.

### Remove — redundant narration

- restates the adjacent code ("increment the counter", "loop over users")
- restates a name, signature, or type the declaration already shows
- internal docstrings that only restate the signature
- change narration addressed to a reviewer ("added this to fix the bug", "NEW:", "updated to handle nulls", "this ensures the fix works")
- decorative section banners that restate structure (but IDE-functional markers like `// MARK:` and `#region` are never-touch)
- commented-out code — git history is where dead code lives
- placeholder scaffolding above finished code ("TODO: implement")
- stale comments the code contradicts — remove, but flag in the summary: the contradiction may mean the code is wrong

Match the surrounding codebase: where the repo enforces a doc-comment convention (godoc on exported symbols, a docstring lint rule), the convention wins even where it feels redundant.

## Comments only

Never modify code — not even a rename that would make a comment unnecessary. When a comment exists because the code is unclear (a bad name, a convoluted expression), apply the doubt rule to the comment and record the observation for the summary. The code fix belongs to a later turn if I want it.

## Summary

Close with a concise report:

- **Counts** — removed / condensed / kept, per file for small scopes, aggregate with notable files for large ones
- **Notable keeps** — comments that looked redundant but survived, and which rule saved them
- **Stale flags** — removed comments that contradicted the code, as possible bugs
- **Code observations** — places where the real fix is the code, not the comment; informational only, nothing changed
